# 场景 B｜Agent SaaS：微信「工作助手」（业务练习项目）

**定位（先读这句）：**  
场景 B **不是**再造一套 Infra，也 **不是**方法论本身。它是挂在 [methodology.md](./methodology.md) 飞轮上的一个**项目**：用场景 A 的底座，做出「能收费的 Agent SaaS」最小闭环，从而**亲自搞懂 Agent SaaS 业务**（获客、用量、成本、邀请制、小 B 席位）。

**一句话产品：** 用户扫码即用，在微信里完成写周报 / 查日志 / 改文档等——不暴露底层网关。

**产品名：** MeClaw（`skills/` + 后期 `hosted/`）。**品类：** Agent SaaS。

**变现顺序：** 邀请制 To C 验付费 → 技能 / 课放大 → 小 B 席位。底座继续反哺场景 A 的开源影响力。

## 和场景 A / 方法论的边界

| | 场景 A（Infra） | 场景 B（本文件） | 方法论 |
|--|-----------------|------------------|--------|
| 是什么 | 自建 claw 能力栈 | **一个 SaaS 落地项目** | 做事方式与飞轮 |
| 目标 | 可私有化、可二次开发 | 验「卖结果」是否成立 | 学习→内容→To B/C 闭环 |
| 代码 | `internal/*` `deploy/` | `skills/` `hosted/` | 文档，不是包 |
| To C | 几乎不做 | **主战场**（邀请制） | 环节名，不是新场景 |
| To B | 私有化主收入 | 可切小 B 席位 / 技能实施 | 环节名，不是新场景 |

**不需要**再开「场景 C = To C」「场景 D = To B」。To C / To B 写在下方「各环节怎么落地」里，作为 B（和 A）的变现动作。

## 各环节怎么落地（B 作为项目时）

| 环节 | 在 B 上怎么落地 |
|------|-----------------|
| **学习** | 提示词与技能包、长任务、人机确认、计费与滥用、微信生态边界；先做 **1 个**垂直技能做深（为「懂 SaaS」服务，不是堆功能） |
| **项目** | MVP：微信对话 → 固定技能（如写周报）；再加用量墙、邀请制；`hosted/` 后期 |
| **对外分析** | 《在微信里改完这个 Bug》《个人 Agent SaaS 成本账》《为什么不做 App 做微信》——素材必须来自自己的 B 试点 |
| **知识付费** | 《30 天做出可收费的微信 Agent》；技能包模板 |
| **自媒体** | 偏结果演示 + 收入/成本透明；人设仍与「自建 claw」总叙事兼容 |
| **To C** | 个人订阅（按量/月卡）；邀请码冷启动；禁止一上来开放注册烧 Token |
| **To B** | 小团队席位、共享知识库、审计；或「帮你配好技能包」实施费——大单私有化仍归场景 A |

## 交付物清单（可勾选）

- [ ] 单一技能 MVP（邀请制可用）——**懂 SaaS 的最小闭环**
- [ ] 用量 / 计费或额度墙（亲自算过成本账）
- [ ] 至少 3 条「结果演示」内容（含成本透明）
- [ ] 技能包模板（至少 1 套可卖或可展示）
- [ ] 小 B 席位或实施试点报价（可选；不替代 A 的私有化 To B）

## 本仓库对应路径

- `skills/` — 技能包（开源可演示；当前有 `examples/weekly-report`）
- `hosted/` — 邀请制 / 用量 / 计费（后期；密钥勿入库）
- 依赖场景 A：`internal/runtime`、gateway、policy 等——**B 不重写底座**

## 建议开工顺序（B）

1. 选定 **1** 个技能（建议周报）写清提示与验收  
2. 本地用 A 的 `chat`/`serve` + `/skill` 跑通演示  
3. 再考虑微信通道与 `hosted/` 邀请墙——通道深度可复用 A 的加深项
